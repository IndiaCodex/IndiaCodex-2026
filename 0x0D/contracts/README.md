# Smart contract — Hydra Minecraft block ledger

The on-chain layer of Hydra Minecraft is the **block-action record**: every voxel
a player places or breaks is written to the Cardano Hydra head as one UTxO
carrying a Plutus **inline datum**. This folder formalises that record and its
rules as an Aiken (Plutus V3) validator.

## Files

| file | what it is |
|---|---|
| `lib/hydra_minecraft/types.ak` | the `BlockAction` datum — `Constr 0 [x, y, z, block_type_id, action, seq]`, the exact Plutus data the relay encodes in [`../server/datum.js`](../server/datum.js), plus a `is_well_formed` guard |
| `validators/block_ledger.ak` | append-only ledger validator: a record UTxO may only be spent by the head **authority** (the relay key), and only if the record is well-formed — history can never be silently rewritten |
| `plutus.json` | compiled CIP-57 blueprint (generated by `aiken build`) |
| `aiken.toml` | project config (Aiken v1.1.21, Plutus V3, stdlib v2.2.0) |

## Datum schema (the on-chain API)

```
BlockAction = Constr 0 [
  x            : Int,   -- world X
  y            : Int,   -- world Y (height)
  z            : Int,   -- world Z
  block_type_id: Int,   -- 0 grass … 8 water, 9 TNT, 10 coal, 11 iron, 12 gold, 13 diamond
  action       : Int,   -- 0 = place, 1 = break
  seq          : Int,   -- replay order
]
```

Because the base terrain is a pure function of a fixed seed, the head's UTxO set
of these records **is the world save file** — replaying them in `seq` order
rebuilds the exact world on any client. This is why the datum is the contract.

## Build & test

```bash
cd contracts
aiken build      # -> plutus.json blueprint
aiken check      # runs the 3 property tests below
```

Verified locally with **Aiken v1.1.21** — `aiken check` → **3 passed, 0 failed**:

- `authority_can_consolidate_well_formed_record` — the head authority may reclaim a valid record's fuel
- `rejects_unsigned_spend` — nobody else can move a record (history is append-only)
- `rejects_out_of_range_block_id` — malformed records are rejected

## How it runs in the demo

The live demo runs a single `hydra-node` in **offline mode** with zero-fee
protocol parameters, so records accumulate as inline datums and are never
spent — the relay signs each block action into the head fire-and-forget (see
[`../server/hydra.js`](../server/hydra.js)). This validator makes the same
append-only rules the relay enforces off-chain **portable to a real,
L1-settled Hydra head**, where the `authority` parameter is instantiated with
the relay's verification-key hash.
